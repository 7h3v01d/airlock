# Airlock — Certification Levels

---

## Overview

Airlock uses a six-tier certification system to communicate the trust status of every artefact in the pipeline. Certification level is not a score — it is a precise statement about which evidence exists, which pipeline stages the artefact has passed, and what execution authority it has been granted.

A higher level does not mean "better code." It means **more evidence, more gates passed, more authority granted.**

Every admitted artefact carries its certification level in its `admission_certificate.json`. Every level has defined entry requirements, defined execution authority, and defined promotion criteria.

---

## The Six Levels

---

### Level 0 — Draft

**Status:** `UNTRUSTED`

**Definition:** Code exists in the project but has not entered the Cleanroom pipeline. It may have been written by hand, copied from another source, or generated by a model outside the Cleanroom workflow.

**Entry requirements:** None. This is the default state of any code that has not been pipeline-processed.

**Execution authority:**
- May not execute in any context
- May not be imported by the trusted runtime
- May not be referenced by admitted artefacts

**Trusted tree:** Not eligible.

**Use case:** Initial sketch, exploratory code, external contributions awaiting pipeline processing.

**Pipeline action required:** Submit to `airlock verify` to begin Level 1 evaluation.

---

### Level 1 — Spec-Aligned

**Status:** `CANDIDATE`

**Definition:** The candidate has been linked to a locked specification and demonstrates structural alignment — its declared API, module boundaries, and stated purpose are consistent with the spec. No critical forbidden behaviours are obviously present.

**Entry requirements:**
- Candidate manifest references a locked spec (`spec_id` + `spec_hash`)
- Candidate passes structural alignment check (public API shape matches spec contracts)
- No critical verifier rules triggered
- All required files present (`src/`, `tests/`, `manifest.json`, `generated_by.json`)

**Execution authority:**
- Sandbox only, no network, no filesystem writes outside sandbox scope
- May not be imported by trusted runtime

**Trusted tree:** Not eligible.

**Use case:** First-pass generated candidate before full verification.

**Pipeline action required:** Pass `airlock verify` to reach Level 2.

---

### Level 2 — Verified

**Status:** `VERIFIED CANDIDATE`

**Definition:** The candidate has passed the full static verifier rule set. All import, filesystem, execution, structural, and dependency rules have been evaluated and no blocking failures exist. The candidate is structurally safe to execute in a controlled test environment.

**Entry requirements:**
- All Level 1 requirements satisfied
- Full verifier run completed with no `severity: critical` or `severity: high` blocking failures
- Dependency scanner completed — no undeclared dependencies, no known-vulnerable packages
- `static_verification.json` produced and hash-sealed

**Execution authority:**
- Controlled test environment (certifier sandbox)
- May not be imported by trusted runtime
- Still quarantined — not in trusted tree

**Trusted tree:** Not eligible.

**Use case:** Candidate ready for test matrix execution.

**Pipeline action required:** Pass `airlock certify` to reach Level 3.

---

### Level 3 — Test-Certified

**Status:** `CERTIFIABLE`

**Definition:** The candidate has passed the required test matrix for its declared risk class. Unit tests, contract tests, and required scenario tests pass. Coverage and mutation score meet policy thresholds. A complete certification evidence set exists.

**Entry requirements:**
- All Level 2 requirements satisfied
- Unit tests: all pass, zero failures
- Contract tests: all pass (derived from `acceptance_criteria.json` and `forbidden_behaviours.json`)
- Usage-model scenario tests: all weighted scenarios pass
- Branch coverage: ≥ policy minimum (default 0.80)
- Mutation score: ≥ policy minimum (default 0.75)
- Additional classes required by risk class:
  - `medium` risk: property tests pass
  - `high` risk: property tests, fuzz tests, security behaviour tests pass
- `test_report.json`, `coverage_report.json`, `mutation_report.json` produced and hash-sealed

**Execution authority:**
- Limited trusted use (can be run in trusted context for validation purposes)
- May be imported in staging/preview contexts
- Not yet in the trusted tree permanently

**Trusted tree:** Eligible — requires governance gate decision.

**Use case:** Candidate ready for governance gate evaluation.

**Pipeline action required:** Pass `airlock gate` to reach Level 4.

---

### Level 4 — Governance-Admitted

**Status:** `TRUSTED ARTEFACT`

**Definition:** The governance gate has evaluated all evidence and issued an ALLOW decision. The candidate has been formally admitted into the trusted tree. An admission certificate has been issued and archived.

**Entry requirements:**
- All Level 3 requirements satisfied
- Governance gate evaluation completed
- Gate decision: `ALLOW`
- All evidence documents verified by gate (hash check)
- Operator approval provided if high-risk permissions present
- `gate_decision.json` and `admission_certificate.json` produced and hash-sealed
- Source tree copied to `trusted/src/` with provenance metadata

**Execution authority:**
- Full trusted execution
- May be imported by trusted runtime
- May be referenced by other admitted artefacts

**Trusted tree:** Present with full evidence linkage.

**Use case:** Production use within the project context. Standard outcome for clean pipeline runs.

**Notes:**
- If admitted via operator override, certificate includes `override: true` and override record reference
- Override admissions are visually distinguished in `airlock report` output

---

### Level 5 — Release-Certified

**Status:** `RELEASE GRADE`

**Definition:** The artefact has been packaged, signed, reproducibly buildable, and linked to complete evidence. It is suitable for distribution, deployment, or inclusion in a downstream project.

**Entry requirements:**
- All Level 4 requirements satisfied
- Release package produced (wheel, sdist, or equivalent)
- Package hash recorded and reproducible build verified
- Complete evidence archive included in or linked from release package
- Release notes authored referencing spec, certification level, and key evidence
- Operator explicit release sign-off recorded

**Execution authority:**
- All Level 4 authority
- May be distributed
- May be included in downstream projects
- May be published to a package registry (local or external, per policy)

**Trusted tree:** Present and release-tagged.

**Use case:** Distributable plugins, certified library releases, artefacts shared across projects.

## Level Summary Table

| Level | Name | Status | Execution Authority | Trusted Tree |
|---|---|---|---|---|
| 0 | Draft | UNTRUSTED | None | No |
| 1 | Spec-Aligned | CANDIDATE | Sandbox only | No |
| 2 | Verified | VERIFIED CANDIDATE | Controlled test env | No |
| 3 | Test-Certified | CERTIFIABLE | Limited trusted use | Eligible |
| 4 | Governance-Admitted | TRUSTED ARTEFACT | Full trusted execution | Yes |
| 5 | Release-Certified | RELEASE GRADE | Full + distributable | Yes + release tag |

## Risk Classes and Minimum Certification Requirements

Risk class determines which test classes are required and which minimum thresholds apply. It is declared in `airlock.yaml` and evaluated by the spec engine's risk register.

| Risk Class | Description | Minimum Cert Level | Additional Requirements |
|---|---|---|---|
| `low` | Read-only, no network, no credentials, no file writes | L3 | Unit + contract + scenario tests |
| `medium` | File writes in scope, no network, no credentials | L3 | + property tests |
| `high` | Network, subprocess, credentials, or file deletion | L4 | + fuzz + security behaviour + operator approval |
| `critical` | Authentication, encryption, payment, data export | L4 | + second operator sign-off + external security review |

## Certification Level in Practice

### In CLI output

```
─────────────────────────────────────────
Candidate:    candidate_0001
Spec:         spec_0001 (v1, locked)
Verifier:     PASS — 24/24 rules
Tests:        PASS — 44/44 unit, 12/12 contract
Coverage:     91% branch
Mutation:     83%
Risk class:   medium
Gate:         ALLOW
─────────────────────────────────────────
Certification Level: L3 — TEST CERTIFIED
Admission status:    ADMITTED (Level 4)
Certificate ID:      al-cert-2026-000001
─────────────────────────────────────────
```

### In reports and documentation

Level should always be communicated with both number and name:

- ✓ "This module is L3 Test-Certified and has been governance-admitted at L4."
- ✓ "The plugin is L2 Verified — not yet test-certified for production use."
- ✗ "The AI says this is good."
- ✗ "Tests pass."

### In evidence archives

The `admission_certificate.json` `level` field uses the canonical string identifier:

```
"L0_DRAFT"
"L1_SPEC_ALIGNED"
"L2_VERIFIED"
"L3_TEST_CERTIFIED"
"L4_GOVERNANCE_ADMITTED"
"L5_RELEASE_CERTIFIED"
```

## Certification Level Downgrade

A previously admitted artefact may be downgraded under the following conditions:

- The locked spec it was certified against is superseded by a new version
- A vulnerability is discovered in a dependency it uses
- A previously passing contract test is found to have been incorrectly authored
- The governance gate is re-evaluated against updated policy and produces a DENY

Downgrade does not automatically remove the artefact from the trusted tree. It raises an alert, marks the certificate as `superseded`, and flags the artefact for re-pipeline or removal. The operator makes the final removal decision, and that decision is logged.
