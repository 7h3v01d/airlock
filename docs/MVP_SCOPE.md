# Airlock — MVP Scope

---

## MVP Philosophy

The MVP must be **conceptually complete but implementation-minimal.** It should demonstrate the full pipeline — from intent to admitted artefact — without implementing the full surface area of every component.

The goal is to prove one thing:

> *A candidate generated by a local LLM can be verified, tested, and governance-gated before it enters a trusted tree — and every step produces durable evidence.*

If the MVP proves that, the platform has a foundation worth building on. If it does not prove that, no amount of feature addition will fix it.

---

## What the MVP Is Not

- It is **not** a multi-language platform. Python only.
- It is **not** a GUI application. CLI only.
- It is **not** a formal verification system. Evidence-grade, not proof-grade.
- It is **not** an autonomous agent. Every significant decision requires operator awareness.
- It is **not** a cloud service. Local filesystem only.
- It is **not** feature-complete. It is the minimal pipeline that is architecturally honest.

---

## MVP Scope

### Supported language

Python 3.11+ only. No JavaScript, Rust, Go, or other targets in the MVP.

### LLM integration

Ollama only. One provider. The provider interface is designed for extensibility but only `OllamaProvider` is implemented.

LLM integration is introduced in **Phase 6** of the build — after the pipeline is proven to work without it. Phases 1–5 operate with manually authored specs and candidates.

### CLI commands

```
airlock init <project_name>     Initialise a cleanroom project structure
airlock spec new                Create a new spec (interactive or --file input)
airlock spec lock <spec_id>     Lock a spec for pipeline use
airlock spec list               List all specs and their status
airlock generate <spec_id>      Generate a candidate using the configured LLM (Phase 6)
airlock verify <candidate_id>   Run the verifier against a candidate
airlock certify <candidate_id>  Run the test certifier against a verified candidate
airlock gate <candidate_id>     Run the governance gate against a certified candidate
airlock admit <candidate_id>    Execute gate-approved admission to the trusted tree
airlock report <candidate_id>   Print the full evidence summary for a candidate
airlock status                  Show project overview: specs, candidates, admitted artefacts
```

### Project structure created by `airlock init`

```
<project_name>/
  airlock.yaml             Project policy configuration
  specs/                     Locked specifications
  candidates/                Quarantined candidates
  evidence/                  All pipeline-produced reports
  trusted/                   Admitted artefacts only
    src/
  logs/
    audit.jsonl              Append-only audit log
```

### `airlock.yaml` — MVP fields

```yaml
project:
  name: my_project
  language: python
  risk_class: medium          # low | medium | high | critical

local_first:
  allow_network: false
  allow_remote_llm: false
  allow_telemetry: false

llm:
  provider: ollama
  model: qwen2.5-coder
  base_url: http://localhost:11434

candidate_policy:
  execute_in_sandbox: true
  allow_subprocess: false
  allow_filesystem_write: sandbox_only
  allow_environment_access: false

verification:
  block_imports:
    - subprocess
    - socket
    - requests
    - urllib
  block_calls:
    - eval
    - exec
    - os.system
  require_type_hints: true
  require_tests: true

certification:
  require_unit_tests: true
  require_contract_tests: true
  require_property_tests: true     # medium+ risk class
  minimum_mutation_score: 0.75
  minimum_branch_coverage: 0.80

governance:
  require_human_approval_for:
    - filesystem_delete
    - network_access
    - subprocess_execution
    - credential_access
```

## MVP Verifier Rules

These are the rules implemented in Phase 3. They cover the highest-value static checks.

### Critical severity (blocking — pipeline stop)

| Rule ID | Check |
|---|---|
| `IMPORT_SUBPROCESS` | `subprocess` imported without policy grant |
| `IMPORT_SOCKET` | `socket` imported without policy grant |
| `IMPORT_REQUESTS` | `requests` imported without policy grant |
| `CALL_EVAL` | `eval()` called anywhere |
| `CALL_EXEC` | `exec()` called anywhere |
| `FS_PATH_TRAVERSAL` | `..` used in path string construction |
| `FS_SYMLINK_ESCAPE` | Symlink resolution not verified against root |
| `MISSING_SPEC_LINK` | Candidate manifest does not reference a locked spec |

### High severity (blocking — pipeline stop)

| Rule ID | Check |
|---|---|
| `IMPORT_URLLIB` | `urllib` imported without policy grant |
| `CALL_OS_SYSTEM` | `os.system()` called |
| `DYNAMIC_IMPORT` | `__import__()` or `importlib.import_module()` used |
| `UNDECLARED_DEPENDENCY` | Import not in declared dependency list |
| `FS_WRITE_OUTSIDE_SCOPE` | File write target outside declared sandbox scope |

### Medium severity (non-blocking — surfaced in report)

| Rule ID | Check |
|---|---|
| `MISSING_TYPE_HINTS` | Functions without type annotations |
| `MISSING_DOCSTRINGS` | Public functions without docstrings |
| `UNPINNED_DEPENDENCY` | Dependency not pinned to exact version |
| `IMPORT_PICKLE` | `pickle` used (flagged, not blocked by default) |

## MVP Test Certifier

The certifier runs the following for all risk classes in the MVP:

- `pytest` — full test suite
- `coverage.py` — branch coverage measurement
- `mutmut` — mutation testing (may be skipped for `low` risk class if slow)
- Contract test runner — tests derived from `acceptance_criteria.json`

For `medium` risk class (default):
- `hypothesis` — property-based tests (must be present in candidate tests)

The certifier does **not** run fuzz testing or security behaviour tests in the MVP. These are planned for Phase 4+.

### Certification report fields (MVP)

```json
{
  "candidate_id": "candidate_0001",
  "spec_id": "spec_0001",
  "risk_class": "medium",
  "certification": "CERTIFIED | NOT_CERTIFIED",
  "unit_tests": {"passed": 0, "failed": 0, "skipped": 0},
  "contract_tests": {"passed": 0, "failed": 0},
  "property_tests": {"passed": 0, "failed": 0},
  "branch_coverage": 0.0,
  "mutation_score": 0.0,
  "blocking_failures": [],
  "certification_level": "L3_TEST_CERTIFIED | null"
}
```

## MVP Governance Gate

The gate implements four decisions:

| Decision | Conditions |
|---|---|
| `ALLOW` | Verifier PASS + all required test classes PASS + policy PASS + evidence complete |
| `DENY` | Any blocking verifier failure OR any required test class failure |
| `QUARANTINE` | Evidence incomplete (missing report, failed hash check, spec not locked) |
| `ESCALATE_TO_OPERATOR` | High-risk permission detected in candidate (network, subprocess, delete, credentials) |

In the MVP, `ESCALATE_TO_OPERATOR` produces a gate report that marks the candidate as pending human decision. The operator responds via `airlock gate --approve <candidate_id>` or `airlock gate --deny <candidate_id>` with a mandatory `--reason` flag.

## MVP Evidence Structure

```
evidence/
  spec_0001/
    spec_meta.json
    spec_hash.txt

  candidate_0001/
    generation_manifest.json
    static_verification.json
    test_report.json
    coverage_report.json
    mutation_report.json
    contract_test_report.json
    gate_decision.json
    admission_certificate.json      (present only if ALLOW)
```

All files are written once and not modified. New pipeline runs produce new evidence sets under a new candidate ID.

## MVP Build Phases

### Phase 0 — Foundation documents ✓

Produce and lock:
- `VISION.md`
- `DOCTRINE.md`
- `ARCHITECTURE.md`
- `THREAT_MODEL.md`
- `CERTIFICATION_LEVELS.md`
- `MVP_SCOPE.md`

This phase is complete when these documents exist, have been reviewed, and represent stable commitments. They are the specification that the MVP is certified against.

---

### Phase 1 — CLI skeleton

Build the CLI harness and project structure without any pipeline logic.

Deliverables:
- `airlock init` creates the correct directory structure and `airlock.yaml`
- `airlock status` reads project state and prints a summary
- `airlock spec list` reads `specs/` and prints status
- `airlock report <candidate_id>` reads `evidence/` and prints a formatted summary

No LLM. No verifier. No certifier. No gate.
Prove the file structure and CLI interface work correctly.

Tests: unit tests for every CLI command, integration test for `airlock init` + `airlock status` on a fresh project.

---

### Phase 2 — Candidate quarantine

Build the candidate store and manifest system.

Deliverables:
- `airlock spec new` creates a spec directory and `spec_meta.json` in `DRAFT` status
- `airlock spec lock <spec_id>` hashes the spec, writes `spec_hash.txt`, updates status to `LOCKED`
- Manual candidate placement: operator copies source to `candidates/candidate_XXXX/src/` and writes `manifest.json` manually
- `airlock status` shows candidates with their status and spec linkage

No LLM. No verifier. Pipeline operates entirely on manually authored specs and candidates.

Tests: unit tests for spec lifecycle, candidate manifest validation, hash production.

---

### Phase 3 — Python verifier

Build the AST-based static verifier.

Deliverables:
- All critical and high severity rules implemented (see MVP Verifier Rules above)
- `airlock verify <candidate_id>` runs the full rule set and writes `static_verification.json`
- Candidate status updated to `VERIFIED` or `REJECTED`
- `airlock report` surfaces verifier results

Tests: one test Python file per rule — a file that triggers the rule and a file that does not. Verifier must correctly classify each.

---

### Phase 4 — Test certifier

Build the certifier pipeline.

Deliverables:
- `airlock certify <candidate_id>` runs pytest, coverage, mutmut, and contract tests in the candidate sandbox
- Produces `test_report.json`, `coverage_report.json`, `mutation_report.json`, `contract_test_report.json`
- All reports hash-sealed
- Candidate status updated to `CERTIFIED` or `NOT_CERTIFIED`
- `airlock report` surfaces certifier results

Tests: use a known-good and known-bad reference candidate for each test class. Certifier must correctly classify both.

---

### Phase 5 — Governance gate

Build the gate and admission system.

Deliverables:
- `airlock gate <candidate_id>` consumes all evidence, evaluates policy, produces `gate_decision.json`
- `airlock admit <candidate_id>` copies source to `trusted/src/`, issues `admission_certificate.json`, appends to `audit.jsonl`
- High-risk escalation path: operator approval via `airlock gate --approve/--deny`
- `airlock report` surfaces full evidence chain including gate decision and certificate

Tests: gate evaluation tests for each decision type (ALLOW, DENY, QUARANTINE, ESCALATE). Evidence hash verification test. Admission test confirming trusted tree contents and audit log entry.

---

### Phase 6 — Local LLM integration (Ollama)

Add LLM-assisted spec drafting and candidate generation.

Deliverables:
- `OllamaProvider` implementing `LLMProvider` interface
- `airlock spec new` with LLM-assisted drafting mode
- `airlock generate <spec_id>` generating a candidate package from a locked spec
- Prompt contracts for `draft_spec`, `generate_candidate`, `explain_failure`
- LLM call logger writing to `logs/llm_calls.jsonl`
- `generation_manifest.json` produced for all LLM-generated candidates

Important: The pipeline from Phase 1–5 must continue to function identically without LLM. LLM is an optional productivity layer, not a pipeline dependency.

Tests: provider interface unit tests with a mock Ollama endpoint. Integration test: generate a candidate, verify it, certify it against a known spec, gate it.

---

### Phase 7 — Dogfood

Use Airlock on its own plugin/extension points.

Target artefacts:
- A custom verifier rule module (certify the verifier's own extensions)
- A Librarian Pro file extractor plugin
- A FileTracker plugin

Goal: find the friction points, missing features, and misleading error messages before building a GUI.

---

### Phase 8 — Dashboard

Build a read-only web or desktop dashboard showing:
- All specs and their status
- All candidates and their pipeline position
- Evidence trail per candidate
- Certification level per admitted artefact
- Audit log viewer
- Risk class distribution

CLI remains the primary interface. Dashboard is observability.

---

## MVP Success Criteria

The MVP is complete when:

1. A Python module can be taken from user intent to governance-admitted artefact using `airlock` commands
2. Every step produces a hash-sealed evidence document
3. A candidate that violates a critical verifier rule cannot be admitted regardless of other results
4. A candidate that fails required tests cannot be admitted
5. Every admitted artefact in `trusted/src/` has a traceable `admission_certificate.json`
6. The audit log contains a complete record of every pipeline decision
7. The pipeline functions entirely without LLM (Phases 1–5 are LLM-free)
8. The test suite for the platform itself passes cleanly

---

## What the MVP Deliberately Excludes

These are not gaps — they are explicit deferrals.

| Excluded | Rationale |
|---|---|
| Multi-language support | Python first; generalisation after validation |
| GUI / web dashboard | CLI proves the pipeline; GUI is Phase 8 |
| Formal verification | Evidence-grade is the correct MVP claim |
| Cloud LLM providers | Local-first; remote providers are Phase 6+ optional |
| Package registry publishing | Phase 5 (Release-Certified) is out of MVP scope |
| VS Code extension | Post-MVP developer experience layer |
| CI/CD integration adapter | Post-MVP; pipeline is standalone first |
| Hash chain (tamper-evident audit log) | Phase 2+ hardening; MVP uses individual file hashes |
| Second operator sign-off for `critical` risk | MVP handles `high` risk; `critical` is post-MVP |
